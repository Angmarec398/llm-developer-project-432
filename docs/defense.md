# Вопросы на защиту (шаг 10)

Ответы опираются на код репозитория; ссылки — на файлы и ADR.

## 1. Где граница между «повторить вызов модели» и «повторить задачу»?

Три уровня. Внутри одного вызова — транспорт и формат: ретраи сети/5xx в клиенте
(`llm_max_retries` в `app/core/config.py`), лечение невалидного JSON через
`call_validated` (`validation_max_attempts`, `app/services/structured.py`): ответ с
текстом ошибки уходит обратно в модель. Между шагами — семантика: петля генерации с
фидбэком критика и проверки ссылок (`max_attempts` в `run_card_pipeline`,
`app/services/cards.py`). Уровень задачи — только инфраструктура: Temporal повторяет
упавшую activity, workflow переживает рестарт воркера. Граница там, потому что повтор
вызова дёшев и не меняет состояния, а повтор задачи виден оператору и пишется в историю —
его повод должен быть осмысленным (сбой процесса, решение человека), а не «модель
ответила криво».

## 2. Почему гибридный поиск находит артикулы, а поиск по смыслу — нет? Что даёт слияние рангов?

Артикул (`KTL-1700`, `BLD-800`) — бессмысленная строка: у векторной модели нет семантики
для неё, косинусная близость с запросом низкая и не проходит порог 0.80 (калибровка —
`docs/adr/0003-retrieval-threshold.md`). Зато полнотекстовый `tsvector` матчит токен в
точности. Обратно: перифраз без точных слов находит только вектор. Оценки двух поисков
несопоставимы (косинус vs ранг tsvector), поэтому сливаются не оценки, а ранги — RRF
`1/(60+ранг)` (`app/repositories/chunks.py`): каждая половина вносит вклад в общий
список, а фрагмент, найденный обеими, всплывает выше.

## 3. Почему маскирование ПДн до вызова модели, а не фильтром на выходе? Зачем тогда фильтр на выходе?

Всё, что попало в промпт, уже утекло: в API модели, в историю Temporal, в логи. Поэтому
маскирование стоит первым рубежом — в `search_chunks` (`app/services/cards.py`), до
сборки контекста и до записи результата activity. Фильтр выхода — вторая линия на другой
класс риска: модель может породить контакты не из контекста (из весов, из склейки
замаскированных кусков) или оставить следы служебных инструкций — это ловит
`filter_card_output` (`app/guardrails/output.py`).

## 4. Как проверка ссылок борется с выдумыванием? Почему мало, что фрагмент существует в базе?

Проверяются два условия (`app/services/citations.py`): фрагмент существует в базе и
входил в контекст этой конкретной генерации. Существования в базе мало: модель может
сослаться на реальный фрагмент, которого не видела, — ссылка выглядит правдоподобно,
проверку «есть в базе» проходит, но утверждение опирается на текст, который модели не
показывали. Это и есть выдумывание с правдоподобным видом. Требование «был в контексте»
делает ссылку проверяемой до конца: нарушение — переделка с текстом ошибки, повтор —
вердикт `citation_fraud` и эскалация к человеку.

## 5. Карточка с низкой уверенностью — действия разработчика на уровне кода и процесса?

Код: `approved` + `confidence < card_confidence_threshold` → вердикт `low_confidence` →
задача в `awaiting_confirmation`, оператор смотрит карточку и сигналит `approve`/`reject`
(`POST /jobs/{id}/approve|reject`). Разработчик расследует по `job_id`: `llm_calls`
(сколько попыток, что отвечала модель), логи (`pipeline_low_confidence`), полноту
контекста — не уперлось ли в порог поиска или в скудный документ (наблюдение из прогона:
один фрагмент `kettle_spec.xlsx`, а модель ставит 0.98 — калибровка уверенности
4B-модели завышена). Процесс: низкая уверенность — не сбой, а маршрут к человеку;
порог — продуктовая настройка, её крутят по накопленной статистике метрик.

## 6. Стоимость карточки выросла втрое за неделю — где искать?

Таблица `llm_calls`: `sum(cost), count(*) by date_trunc('day', created_at)` — вырос
объём вызовов или цена за вызов; разрез по `agent`/`model` — кто разбух; разрез по
`job_id` — задачи-рекордсмены; `prompt_tokens` vs `completion_tokens` — вырос контекст
(больше фрагментов, длиннее документы) или ответы. Дальше `jobs.attempts` — выросло ли
число переделок (критик чаще возвращает на доработку) и логи `pipeline_regenerate` /
`injection_verdict_healing` — частота лечений и регенераций. Локальные модели цену не
меняют — значит, почти наверняка объём: больше попыток или больше контекста.

## 7. Почему состояние задачи в базе, а не только в истории движка? Что при рестарте воркера?

История Temporal — журнал событий для восстановления, а не модель для чтения: выборка
статуса из неё дорогая и неудобная. `jobs` — материализованное представление для
продукта: дешёвый SELECT, `GET /jobs/{id}`, результат и отчёт защиты в JSONB. При
рестарте воркера workflow восстанавливается детерминированным replay с последнего
события; activity, не успевшая завершиться, выполнится заново — поэтому все activities
идемпотентны (`set_status` по job_id, эмбеддинги только отсутствующим, документ по
`content_hash`).

## 8. Детектор инъекций не смог обратиться к модели — что делает сервис?

Fail-closed (`docs/adr/0006-guardrails-fail-closed.md`): мусорный/недоступный ответ
после всех попыток лечения = защита не сработала = фрагмент подозрительный. Он
исключается из контекста, при доле выше `injection_document_threshold` документ уходит
в карантин, чистых фрагментов нет — задача в `awaiting_confirmation`, генерации не
происходит. Логика: молчаливо пропустить фрагмент при отказавшей защите — значит
открыть дыру; ложная блокировка обратима (человек разберётся), пропущенная инъекция —
нет. Вживую видели мягкий вариант в прогоне: `injection_verdict_healing attempt=1` —
вердикт починился полным повтором с текстом ошибки.
