# 3. Порог релевантности и выбор модели эмбеддингов (шаг 6)

## Контекст

Поиск по фрагментам — три режима: по векторам (косинусная близость),
по словам (ts_rank), гибрид (слияние по обратным позициям, RRF).
Порог один — `retrieval_score_threshold`; по условию шага он
откалиброван на своих данных, а не взят с потолка.

Замеры на корпусе из четырёх документов поставщика, запросы из
проверки шага («какая мощность у блендера», «мотор 800 Вт»,
«KTL-1700»):

- верные страницы по смыслу: 0.850–0.866;
- тематический хвост (соседние разделы о технике того же поставщика): 0.819–0.838;
- офисный мусор (ОГРН, email менеджера): 0.796–0.804;
- полнотекстовые оценки живут на другом масштабе: точное совпадение
  артикула — 0.0996, перефразированный запрос со всеми словами
  на месте — 2.4e-07.

## Решение

Порог 0.80: верные результаты проходят с запасом ~0.05, мусор
отсекается. Порог применяется к оценке режима: в векторном — к
косинусной близости, в полнотекстовом — к ts_rank, поэтому режим
по словам при умолчанию возвращает пусто: его оценки на порядки
ниже порога. Это сознательный обмен — мусор в контекст дороже
пропуска, а демонстрация словесного поиска идёт с `--min-score 0`.
В гибриде порог фильтрует только векторную половину: полнотекстовый
кандидат — точное совпадение термина, он релевантен по построению,
так гибрид находит и артикулы. RRF: вклад 1/(60+ранг) от каждого
списка, где фрагмент найден, найденный обоими всплывает выше.

Модель эмбеддингов — intfloat/multilingual-e5-small через
sentence-transformers, не LM Studio: префиксы "query: "/"passage: "
часть контракта модели и подставляются в app/rag/embedder.py,
модель грузится один раз на процесс, векторы считаются пачкой.

## Последствия

- Смена модели эмбеддингов = новая миграция колонки vector(384)
  и перекалибровка порога.
- GGUF-конверсии эмбеддинговых моделей непригодны без проверки
  качества: keisuke-miyako/multilingual-e5-small-gguf-q8_0 через
  LM Studio выдавала дегенеративные векторы (близость перефразировки
  1.0000, любой мусор ≥ 0.91), поиск молча не работал.
- pgvector 0.5.1 не дампит list[float] в vector — на границе
  репозитория векторы оборачиваются в pgvector.Vector.
