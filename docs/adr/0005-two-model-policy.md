# 5. Политика двух моделей и модель-судья для метрики истинности (шаг 8)

## Контекст

Служебные вызовы (критик, судья) не требуют сильной модели, основная
генерация — требует. Отдельно: третья метрика качества (истинность)
по спецификации считается самой моделью, и спецификация сама
предупреждает, что судья — приём спорный, его число — оценка, а не
истина.

## Решение

Две записи в настройках: llm_model (генерация) и llm_model_utility
(критик, судья), у каждой свои цены за миллион токенов; клиент
выбирает цены по имени модели агента. В клиенте — MultiProvider с
unknown_prefix_mode="model_id": без него SDK разбирает имя модели как
«провайдер:модель» и падает с Unknown prefix на именах вида
«unsloth/qwen3-…».

Судья (judge_agent, служебная модель) возвращает только разметку:
{supported: [...], unsupported: [...]}. Долю подтверждённых считает
детерминированный код (evals/metrics.py) — модель не вычисляет саму
метрику, это защищает метрику от «приукрашивания» судьёй.

## Последствия

- Экономия видна в разбивке llm_calls: служебная модель в ~20 раз
  дешевле основной при сопоставимом объёме токенов.
- Истинность недетерминирована: 0.38–0.56 на одном документе между
  прогонами. Сравнивать тренды по отчётам, а не точные значения.
- Судья на слабой модели строг: общие места карточек уходят в
  unsupported, поэтому метрика ниже детерминированных (0.60 против
  1.00/0.75 на полном прогоне).
